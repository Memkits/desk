2 技术选型

标准不是性能，而是你能不能维护得了它。每一块都应能在需要时替换。

全托管自己管
前端 / 函数Vercel、Netlify、Cloudflare 等托管平台云服务器 + Docker Compose，或 Fly.io、Render、Railway 等容器平台
数据库托管 Postgres（如 Neon、Supabase）自己跑 Postgres（或仍用托管）
登录 · 邮件 · 支付现成服务（如 Auth.js / Clerk；Resend / Postmark；Stripe）同左，尽量不自建
优点几乎不碰服务器，起步快成本可控、可迁移、更自由
代价月费随用量上涨；被平台绑住的程度备份、升级、补丁、监控都是你的事
用户主要在国内时，国内云厂商也有对应的托管服务和服务器产品，思路相同；网络、合规和可选服务范围不同，按实际情况选。

17 事故处理

发现→止损→定位→恢复→复盘
阶段案例：支付回调失败
发现告警：已付款但报名状态未更新的数量上升
止损确认影响范围；若由刚才的发布引起先回滚；不确定时先挂提示“付款已收到，确认邮件稍后送达”
定位错误上报：验签失败；部署记录：生产环境变量被换成了测试模式的密钥
恢复改回密钥；支付服务重试失败的回调，幂等处理自动补上状态；超过重试期的用对账脚本补齐
复盘写下经过、影响、为什么没更早发现、如何防止（如启动时检测到生产使用测试密钥就拒绝启动）；不追究个人

22 AI 参与运维

可以交给 AI必须人确认（或只给只读权限）
读告警和日志，总结发生了什么直接修改生产数据库

实用做法：给代理一个只读的生产账号（日志 / 指标查看、数据库只读副本），没有部署、密钥、账单权限；改动走 PR → 流水线 → 人审。
